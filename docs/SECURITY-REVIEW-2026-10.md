## 1. לקוח משלם ולא מקבל רישיון — **אומת בהרצה**

**הבעיה.** מזהה התיבה של מנהל-העל הוא מזהה מפתח השורש — ציבורי. כל אחד יכול ליצור זוג מפתחות
חדש בחינם ולשלוח 50 הודעות בבקשה אחת. אחרי 500 הודעות התיבה "מלאה".
ב-`webhook()` הסטטוס נכתב `paid` **לפני** `deliver()`. כש-`deliver` נכשל ב-507, ספק הסליקה מנסה שוב,
והשרת עונה `duplicate: true` כי הסטטוס כבר אינו `pending`. ההרשמה לא נמסרת לעולם.

**ההוכחה.** 10 בקשות מ-10 מפתחות ו-10 כתובות IP מילאו את התיבה. ה-webhook הראשון החזיר 507,
הסטטוס נשאר `paid`, הניסיון החוזר החזיר `duplicate`, ובתיבת מנהל-העל אין הודעת `signup`.

**תיקון מוצע.**
- לשמור את הרשמות ששולמו בקובץ נפרד (`deliveries.json`) שאינו כפוף ל-`MAX_MAILBOX`,
  או לפטור הודעות `from: 'relay'` מהתקרה.
- לכתוב `paid` רק אחרי שהמסירה הצליחה, או לסמן `paid_undelivered` ולנסות שוב בכל `fetch` של מנהל-העל.
- לשלוח לתיבה רק משולחים שיש להם קשר מוכר (בעלי רישיון / בקשת רישיון אחת לכל מפתח),
  ולהגביל הודעות לכל מפתח שולח, לא רק לכל IP.
- בדיקת רגרסיה: תיבה מלאה ← webhook ← ההרשמה בכל זאת מגיעה למנהל-העל.

## 2. שכבת הסנכרון מקבלת `store = null` — **אומת בהרצה**

```js
// modules/econ/ipc.js
115  licenseSync = createLicenseSync({ store: licenseStore, ... });   // licenseStore עדיין null
117  licenseStore = LS.createLicenseStore({ ... });
```

`createLicenseSync` שומר את הערך שקיבל, ו-`initEcon` נקרא פעם אחת בלבד (`main.js:493`).
לכן `store` בתוך הסנכרון הוא `null` לתמיד. כל פעולה מרחוק — סנכרון, בקשת רישיון, הרשמה,
הודעות, הצעה — זורקת `TypeError: Cannot read properties of null`, והמשתמש רואה "הפעולה נכשלה עקב שגיאה פנימית".

הבדיקות עוברות כי הן בודקות את `createLicenseSync` ישירות עם `store` תקין, ולא דרך `initEcon`.
**הבאג קיים גם בגרסה של הסשן המקביל** (שורות 124/128 שם).

**תיקון:** להחליף את סדר השורות 115 ו-117, ולהוסיף בדיקה שקוראת ל-`license:getRemote` /
`license:remoteSync` אחרי `initEcon` אמיתי.

## 3. הרישוי כבוי בבנייה

`shell/licensing/root-keys.js` מייצא `[]`. בלי מפתח שורש:
- `store.current()` מחזיר `unlicensed` — **כל המודולים פתוחים לכולם**, בלי רישיון.
- `verifyRelease` זורק "מפתח מנהל-העל אינו מוגדר" — **אי אפשר לאמת עדכונים**.
- הסנכרון שולח לתיבה של מפתח מנהל-העל המקומי, שקיים רק במחשב של מנהל-העל.

ההערה בקובץ מציינת שזה מכוון עד "שלב 3". אבל README של 3.9.0 מציג את הרישוי כתכונה פעילה.
**לפני שמוכרים רישיון — יש להכניס את המפתח הציבורי**, ולהוסיף בדיקה ב-`tests/build-config.test.js`
שנכשלת אם בונים גרסת הפצה כש-`root-keys.js` ריק.

## 4. מצב מרוץ ב-`payments.json`

`checkout()` קורא את `payments.json`, ממתין ל-`provider.createCheckout()` (קריאת רשת אצל ספק אמיתי),
ורק אז כותב `[...all, חדש]`. אם בזמן ההמתנה נכתב עדכון אחר (checkout נוסף או webhook) — הוא נדרס:
- שני checkout במקביל ← אחת הרשומות נעלמת ← ה-webhook שלה מחזיר 404 ← **שולם, אין רשומה**.
- webhook שסימן `paid` נדרס חזרה ל-`pending` ← בניסיון חוזר של הספק ההרשמה נמסרת **פעמיים**.

**תיקון:** תור סדרתי (כמו `enqueue` בתוכנה) לכל קריאה-שינוי-כתיבה של `payments.json`,
וקריאה מחדש של הקובץ **אחרי** ה-`await`.

## 5. הגבלת קצב לפי IP מאחורי שרת TLS

הקובץ ממליץ להריץ "מאחורי שרת שמספק TLS". במצב כזה `req.socket.remoteAddress` הוא תמיד
כתובת הפרוקסי, וכל הלקוחות חולקים מכסה אחת של 60 בקשות לדקה. לקוח אחד עמוס (או תוקף) חוסם את כולם.

**תיקון:** אפשרות `--trust-proxy` שקוראת את `X-Forwarded-For` (רק כשהיא מוגדרת),
ובנוסף הגבלה לפי מזהה המפתח המאומת.

## 6. עקיפת רישוי דרך `people:*` ו-`privacy:*` — **אומת בהרצה**

`featuresForChannel` דורש לתחילית שאינה ב-`ECON_SUB_FEATURES` רק את `econ`. אבל:
- `people:*` בונה כרטיס אדם מעמותה, גמ"ח, חסד והוראות קבע.
- `privacy:*` מציג ספירות ופרטים מכל המאגרים.

ברישיון עם `econ` בלבד: `chesed:getOverview` נחסם, אבל `people:list` ו-`privacy:getMap` **עוברים**.
מערכת שהתחום נסגר לה ממשיכה לראות נתוני נזקקים וגמ"ח דרך מאגר האנשים.

**תיקון:** ב-`peopleService` לסנן מקורות לפי הרישיון (רק תחומים פתוחים), או לדרוש ב-`people:` לפחות
אחד מתחומי המקור. להוסיף לבדיקת `licensing-gate` את שתי התחיליות.

## 7. עריכת קובץ הרישוי מבטלת השבתה ומאפשרת החזרת שעון

מצב הרישוי (`chain`, `notices`, `lastSeen`) נשמר ב-JSON גלוי. ההערה ב-`mergeNotices` אומרת
"אף פעם לא מחיקה (כך שאי אפשר לשכוח השבתה)" — אבל זה נכון רק לקוד. משתמש עם גישה לקובץ יכול:
- למחוק את מערך `notices` ← השבתה ונעילה בוטלו.
- לאפס את `lastSeen` ולהחזיר את שעון Windows ← הרישיון "פעיל" שוב אחרי שפג.

באכיפה אופליין אי אפשר למנוע זאת לגמרי, אבל אפשר להקשות מאוד:
- חתימת HMAC על הקובץ במפתח שנשמר ב-DPAPI (כמו מפתח הצומת). קובץ שלא מאומת ← `locked`.
- לשמור `lastSeen` ו"סימן מים" של מספר ההודעות גם בתוך קובץ המפתח המוצפן.

## 8. ספק התשלום לבדיקות זמין בייצור

`--pay test` מפעיל דף שבו כל אחד לוחץ "תשלום מוצלח" ומקבל רישיון בתשלום בחינם.
ההגנה היחידה היא `console.warn`. טעות בפקודת ההפעלה בשרת אמיתי = רישיונות בחינם.

**תיקון:** לסרב להפעיל `test` אלא אם מוגדר `SS_ALLOW_TEST_PAYMENTS=1`, ולסרב תמיד כשמופעל עם `--cert`.

## 9. הודעות: מפתח קבוע, בלי סודיות קדימה

ההצפנה היא X25519 סטטי-סטטי, מאותו מפתח Ed25519 שמשמש לחתימה. דליפת מפתח של מערכת אחת
חושפת את **כל** ההודעות שנשמרו בשרת בעבר. ההצפנה והחתימה עצמן תקינות (GCM + חתימה על התוכן).
**הסשן המקביל כבר עובד על זה** (commit `716a048`, "סודיות קדימה") — אין צורך בעבודה נוספת כאן.

שולי: `JSON.parse` בשורה 68 אינו עטוף — תוכן מפוענח פגום יזרוק שגיאה באנגלית (נתפסת ב-`toUserError`).

## 10. הורדת עדכון בלי תקרת גודל

כש-`content-length` חסר, `res.arrayBuffer()` טוען הכול לזיכרון. שרת עוין (הקישור בתעודה חתום,
אבל השרת עצמו לא מהימן) יכול לשלוח גיגה-בייטים ולהפיל את התוכנה. החתימה עדיין מגינה מהתקנה —
זו רק בעיית יציבות. **תיקון:** קריאה בזרם עם עצירה ב-`payload.size + 1`.

## 11. `hits` בשרת גדל ללא גבול

כתובת IP שהפסיקה לפנות נשארת ב-Map לתמיד. בשרת שרץ חודשים — דליפת זיכרון איטית.
**תיקון:** ניקוי תקופתי של רשומות ריקות (כמו שנעשה ל-`nonces`).

## מה נבדק ונמצא תקין

- **שרשרת הרישיונות:** אימות Ed25519, JSON קנוני, השוואה קנונית שתופסת שדות עודפים,
  "הילד לא מקבל יותר מההורה", אישור חתום של מנהל-העל לכל מערכת בת, קשירת רישיון למפתח המכשיר.
- **עדכונים:** חתימה, איסור שנמוך, SHA-256 וגודל, בדיקה חוזרת לפני הרצה, נתיב בתוך `updates`, https בלבד.
- **שרת:** אימות חתימה על כל בקשה, חלון זמן, nonce נגד שידור חוזר, בדיקת `to` ב-regex (אין path traversal),
  תקרות גודל, HSTS ו-nosniff, `redirect: 'error'` בלקוח.
- **הרשמה:** הסכום נקבע מההצעה החתומה בלבד, ונבדק מול סכום ה-webhook. HMAC ב-`timingSafeEqual`.
- **IPC:** ערוצי `owner:` / `license:` / `update:` דורשים `users.manage`. פתיחת דף תשלום — https בלבד.
