# פיצול SuperSuite כלכלה לשלוש תוכנות — תכנית

סטטוס: **ממתין לאישור הבעלים** (5.11.2026). שום קוד לא נכתב עדיין.

## החלטות הבעלים (5.11.2026)

| נושא | החלטה |
|------|--------|
| מבנה | **שלושה מאגרים נפרדים** בסוף הדרך — אבל **קודם שלב ביניים כאן**: הקוד מופרד במאגר הזה למהדורות, ורק אחר כך עובר למאגרים |
| לקוחות קיימים | **גרסה רביעית "מלאה"**: כל התוכנות, **כולל הלימוד**, בתוכנה אחת — ממנה הבעלים מנהל את הכול. הלקוחות הקיימים נשארים עליה |
| חשבוניות במהדורות האחרות | **המנוע ויומן החשבונות בכל מהדורה מאחורי הקלעים**; מסכי הנהלת החשבונות המלאים — רק בחשבונאות (ובמלאה) |
| אנדרואיד | **עדיין לא.** האפליקציה הקיימת לא משתנה; אין מפתח חתימה חדש |
| אתר | **דף אחד עם שלושה כרטיסים** |
| רישוי | **תכנית אחת לכל מוצר**; המחיר — בהמשך, במסך מנהל-העל |

## החלוקה

| מהדורה (`id`) | שם | תחומים (תכונות רישיון) | מודולים |
|---|---|---|---|
| `npo` | SuperSuite עמותות | `econ.npo`, `econ.gemach`, `econ.chesed` (+ מאגר אנשים) | econ, tools |
| `realty` | SuperSuite נדל"ן ועסקים | `econ.realestate` (שמאות מקרקעין + תיווך ויזמים), `econ.mortgage-advisor`, `econ.mortgage-lab`, `econ.mortgage`, `shamai` | econ, shamai, tools |
| `acct` | SuperSuite חשבונאות | `econ.accounting` (חשבוניות, מסמכי מכירה, מע"מ, PCN874, קובץ אחיד, בנק, דוחות, חוזרת, גבייה), משק בית (`personalFinance:*` / `personal:*`) | econ, tools |
| `full` | SuperSuite (מלאה) | הכול, כולל הלימוד | econ, shamai, tools, trainer |
| בכל המהדורות | — | ארגז הכלים, AI, מסך הבית, נגישות ומצב פשוט, משתמשים והרשאות, גיבוי ושחזור, רישוי, הודעות, אנשי קשר, משימות | |

**מנוע החשבוניות "מאחורי הקלעים"** בעמותות ובנדל"ן: `madv:issueFeeInvoice`, `rlty:issueCommissionInvoice` ו-`collect:*` של התחום ממשיכים לעבוד דרך `accountingService`. מסכי `acct-*` וערוצי `acct:*` ישירים — סגורים, חוץ מרשימה סגורה שהמהדורה צריכה (לפחות: הדפסת חשבונית שהופקה, רשימת החשבוניות של התחום, הגדרות העסק שמודפסות על החשבונית). הרשימה המדויקת — בשלב 1, לפי מה שהמסכים של כל מהדורה קוראים בפועל, עם בדיקה.

## עקרונות

- **מקור אמת אחד: `shell/edition.js`** (טהור, בלי require — נטען גם במעטפת). לכל מהדורה: `id`, שם, `appId`, צבע מוביל, `mods`, `features` (תת-קבוצה של `offer.FEATURES`), תחיליות ערוצים מותרות, רשימת ערוצי `acct:*` "מאחורי הקלעים", פריטי קטלוג / פרופילי פתיחה / משימות.
  המהדורה נקבעת **בזמן הבנייה** (`SS_PRODUCT=npo|realty|acct|full` ← קובץ `shell/edition-id.js` שנוצר בבנייה; בלי דגל = `full`, כדי שהמצב הקיים לא ישתנה).
- **מהדורה ∩ רישיון ∩ תפקיד.** `runGuarded` ב-`ipc.js` בודק את המהדורה **לפני** הרישיון: ערוץ של תחום שלא במהדורה ← "התחום הזה אינו חלק מ-<שם המהדורה>". גם `main.js` (`MODS`, `shell:open`, `shell:start-task`, נגישות מודולים) ו-`login-gate`.
  בדיקה בסגנון `tests/login-required.test.js`: **כל** ערוץ ב-preload × כל מהדורה ← מותר / נדחה לפי `edition.js`.
- **רישיון:** תכנית בהצעה מקבלת שדה `edition` (ההצעה החתומה כבר כוללת תכניות; שדה לא מוכר בגרסה ישנה — נבדק שלא שובר אימות). רישיון עם תכונות של מהדורה אחרת נטען כרגיל, והתכונות האלה פשוט לא פותחות דבר (כמו `LEGACY_FEATURES`). מסך הרכישה מציג רק תכניות של המהדורה.
- **נתונים וגיבוי:**
  - כל מהדורה — `appId` ותיקיית נתונים משלה. **המלאה שומרת על `com.bunimseller.supersuite` ועל התיקייה הקיימת** — לקוח קיים לא מרגיש שינוי.
  - פורמט הגיבוי לא משתנה. גיבוי מהמלאה משוחזר בכל מהדורה; **נתוני תחומים אחרים נשמרים במסד ולא נמחקים** (כמו `fitnessData`), ולא מוצגים. גיבוי שנעשה במהדורה כולל גם אותם — כך המעבר בין מהדורות לא מאבד דבר.
  - חלון אישור השחזור מציין "יש בגיבוי גם נתונים של … — הם נשמרים ולא מוצגים במהדורה זו".
- **מצב פשוט ותיבת הפקודה:** `tasks.js` / `simple-mode.js` / `intents.js` / `onboarding.js` מסננים לפי המהדורה; `intents.parse` לא מציע משימה שלא קיימת (בדיקה לכל מהדורה).
- **כללי הברזל** — בלי חריגה: אפס רשת, CSP, הצפנה, אגורות, עברית ו-RTL.

## שלבים (ענף ו-PR טיוטה לכל שלב; `npm test` עובר בסוף כל שלב)

1. **`shell/edition.js` ואכיפה** — הקובץ, דגל הבנייה, אכיפה ב-`runGuarded` וב-`main.js`, סינון קטלוג / מסך בית / חיפוש / אשף / משימות / תיבת הפקודה. ברירת המחדל `full` = ההתנהגות של היום. בדיקות: כל ערוץ × כל מהדורה, קטלוג, משימות, שחזור גיבוי מלא במהדורה חלקית (נתונים נשמרים).
2. **רישוי** — `edition` בתכנית, מסך מנהל-העל מנפיק תכנית לכל מהדורה (מחיר ריק עד החלטה), מסך הרכישה מסנן. בדיקות ב-`audit-licensing-*`.
3. **בנייה** — `package.json` → תצורה לכל מהדורה (`appId`, `productName`, שם קובץ, סמל, `nsis`), `build-local.js --product`, `build-exe.bat` (בחירה / כולן), `.github/workflows/build.yml` בונה ארבעה מתקינים **בתוך משימת `build` האחת, בלולאה** (לא matrix — מלכודת המכסה). קובץ הנעילה מתעדכן אם התלויות משתנות. סמלים: `build/icon-<id>.svg` ← `tools/make-icon.js`. 🔧 בדיקה ב-Windows.
4. **אתר** — `docs/website` ו-`deploy/site`: דף אחד עם שלושה כרטיסים (+ הפניה למלאה ללקוחות קיימים).
5. **המהדורה המלאה כוללת את הלימוד** — דורש גישה למאגר של SuperSuite לימוד (`add_repo`) ושינוי הכלל "אין להחזיר לכאן קוד שלו" ב-`CLAUDE.md` (הכלל יהפוך ל"קוד הלימוד — רק במהדורה `full`"). `legacy-modules.js` נשאר לשאר המהדורות. **שלב נפרד, אחרי החלטה סופית** — ראו שאלה פתוחה 2.
6. **מעבר לשלושה מאגרים** — `tools/split-product.js <id> <יעד>`: מעתיק רק את הקבצים שהמהדורה צריכה (לפי `edition.js` ומפת תלויות של `require`), קובע את המהדורה קבועה, ומריץ את הבדיקות של אותה מהדורה בעותק. הבעלים יוצר שלושה מאגרים ריקים ב-GitHub (אני לא יכול ליצור מאגר מכאן), ואז דוחפים אליהם. המאגר הזה נשאר המלאה.

## שאלות פתוחות לבעלים (לא חוסמות את שלבים 1–3)

1. **המחירים** לכל תכנית — במסך מנהל-העל, כשתחליט.
2. **הלימוד במלאה:** האם המלאה נמכרת גם ללקוחות (עם נתוני בריאות של הלימוד — דורש את ההגנות שהיו שם), או רק לך ולקוחות קיימים? וגם — האם מוצר הלימוד הנפרד ממשיך להתקיים במקביל?
3. **שמות המאגרים** החדשים ב-GitHub.
4. **צבעים וסמלים** — הצעה: עמותות ירוק, נדל"ן כחול, חשבונאות סגול; המלאה — הצבע של היום.
