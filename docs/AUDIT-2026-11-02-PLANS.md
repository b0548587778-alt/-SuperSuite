שלושה ממצאים מחייבים שינוי במבנה האחסון או תכנון רחב. **לא בוצעו** — ממתינים לאישור הבעלים (⏸ בדוח `docs/CODE-AUDIT-2026-11-02.md`).

## א. שמאי — מפתח אחסון לכל תיק (`modules/shamai/src/casefile.js`)

**היום:** כל התיקים במפתח אחד (`shamai_v2_cases`, תקרה של 5MB לערך) — השמירה נעצרת בסביבות 1,000 תיקים.

1. **מבנה:** `case_<id>` לכל תיק (כולל `history`/`snapshot`), ומפתח אינדקס קטן `casesIndex` — `{ v:1, ids, rows:[{id,no,rev,status,clientName,idNumber,clientKey,effectiveDate,purpose,totalAg}] }`. מסכי הרשימה וההיסטוריה קוראים רק אותו. `casePhoto_*` ו-`caseSeq` — בלי שינוי.
2. **סדר כתיבה:** התיק ואז האינדקס; מחיקה — אינדקס ← תיק ← תמונות. בעלייה: מפתח תיק שחסר באינדקס (קריסה) מתווסף; רשומת אינדקס בלי מפתח — נמחקת.
3. **הגירה בטעינה:** יש `cases` ואין `casesIndex` ← כתיבת כל `case_<id>` ואז האינדקס ← אימות (קריאה חוזרת והשוואת JSON) ← `ImageDB.flushStore()` ← רק אז הסרת `cases`. כשל ← `cases` נשאר המקור, ניסיון חוזר בטעינה הבאה, בלי מחיקה. סימון `casesMigratedAt`.
4. **גיבוי ושחזור:** הגיבוי המוצפן מעתיק את כל פריטי המחסן — המפתחות החדשים נכללים, הפורמט לא משתנה. גיבוי ישן (עם `cases`) ← `replaceAll` מחזיר אותו והטעינה הבאה מגירה שוב. גיבוי חדש בגרסה ישנה — יאבד תיקים: סימון סכמה בגיבוי והודעה בעברית, או שחרור בשני שלבים (סעיף 6). לעדכן גם את `shamaiContext` (הקשר ה-AI) ואת "מחק את כל הנתונים" (`KEEP_ON_CLEAR`).
5. **חזרה לאחור:** קריאה של `cases` הישן לגרסה אחת, ועותק `cases.bak` עד ה-flush המוצלח הבא.
6. **שחרור בשני שלבים:** גרסה N קוראת את שני המבנים וכותבת עדיין `cases`; גרסה N+1 מגירה וכותבת את החדש.
7. **בדיקות:** הגירה הלוך-חזור, קריסה בין השלבים, גיבוי ישן למחסן חדש, יותר מ-1,000 תיקים, מכסה לכל מפתח.

## ב. מחסן השמאות המוצפן — תמונות בנפרד (`shell/secure-store.js`)

**היום:** `secure-shamai.bin` אחד עם תקרה של 64MB לכל הנתונים והתמונות, וכל כתיבה מצפינה וכותבת את כל הקובץ בתהליך הראשי.

1. **מבנה:** `secure-shamai.bin` לנתונים בלבד (תקרה, למשל 32MB) + תיקייה `secure-shamai-blobs/` — קובץ לכל תמונה (שם = SHA-256 של המפתח, AES-GCM באותו מפתח נגזר, כתיבה אטומית). מכסה נפרדת לתמונות (למשל 512MB). רשימת מפתחות התמונות נשמרת בקובץ הראשי, כך ש-`key()` / `length` ממשיכים לעבוד. ממשק ה-preload (`write(op,k,v)`) לא משתנה; הניתוב לפי תחילית (`img_`, `casePhoto_`).
2. **טעינה עצלה:** היום `secure-store:load` שולח לעמוד את כל הפריטים. תמונות ייטענו לפי דרישה בערוץ sync חדש `secure-store:get` (`fromModuleView` + `secureWriteBlock` לכתיבה) — משנה את `ImageDB.load` / `loadCasePhoto`. זה שינוי תכנון.
3. **הגירה בפתיחה:** תמונות בקובץ הראשי ← כתיבת קבצי blob ← flush ואימות פענוח ← כתיבת הקובץ הראשי בלי התמונות. כשל ← התמונה נשארת בקובץ הראשי; ההגירה ממשיכה בפתיחה הבאה.
4. **גיבוי ושחזור:** `readModuleItems` ממזג את הקבצים חזרה — פורמט הגיבוי לא משתנה. `replaceAll` מפצל. החזרה למצב הקודם בשחזור — גם לתיקיית הקבצים (כתיבה לתיקיית ביניים והחלפה). מצב בלי DPAPI (`LEGACY_LS_WORLD`) — דורש החלטה.
5. **חזרה לאחור:** כתיבה כפולה לגרסה אחת, או השארת עותקי התמונות בקובץ הראשי עד גרסה N+1.
6. **אנדרואיד** (`frame.js` / `SqlBridge`, חלון 64MB) — החלטה נפרדת.
7. **בדיקות:** הרחבת `audit-secure-store(-plain)` — ניתוב, מכסות, המשך הגירה, חזרה בשחזור עם קבצים, כשל flush בתיקייה.

## ג. מסד הנתונים הכלכלי — מטמון ושמירה חלקית (`modules/econ/core/database.js`)

**היום:** כל `load()` מפענח את כל האוספים, וכל `save()` מוחק ומצפין-כותב את כולם (3,000 חשבוניות ו-10,000 תרומות: כשליש שנייה להפקת חשבונית; 50,000 תרומות — 1.7 שניות).

**אין שינוי בפורמט על הדיסק ואין הגירת נתונים.**

1. **מטמון בזיכרון:** לכל אוסף — `{ sealed, json }` (המחרוזת המוצפנת כפי שנקראה מהמסד ו-JSON המפוענח). `load()` קורא את השורות; שורה שהמחרוזת המוצפנת שלה זהה למטמון — בלי פענוח, רק `JSON.parse(json)` (עותק טרי, כך שהשירותים לא משנים את המטמון).
2. **שמירה חלקית:** `save()` מסדר כל אוסף ל-JSON ומשווה למטמון; רק אוספים שהשתנו נכתבים (`INSERT … ON CONFLICT DO UPDATE` במקום `DELETE` של הכול), באותה טרנזקציה אחת. המטמון מתעדכן רק אחרי `COMMIT`.
3. **ביטול המטמון:** בכל `restore`, מיגרציה, `_encryptExisting`, החלפת מפתח, ו-ROLLBACK. כתיבה שעוקפת את `save` אסורה ממילא (כלל 5 / `cipher.seal`).
4. **סיכונים:** מטמון שלא בוטל אחרי כתיבה חיצונית ← נתונים ישנים. בדיקות: שמירה של אוסף אחד כותבת שורה אחת; שחזור מבטל מטמון; ROLLBACK לא משאיר מטמון מלוכלך; אנדרואיד (`SqlBridge`) עם אותה התנהגות; השוואת ביצועים ב-10,000 תרומות.
