## מה נבדק ואיך

כל ממצא בדוח אומת בקריאת הקוד עצמו, ורובם גם בהרצה בפועל (מסומן ✔ הורץ).

| תחום | נבדק | שיטה |
|---|---|---|
| 1. הרשאות וכניסה | מלא | קריאת `ipc.js`, `authService.js`, `database.js`, כל ערוצי `main.js`; מיפוי אוטומטי של כל 397 הערוצים להרשאה הנדרשת |
| 2. הצפנה וגיבויים | מלא | קריאת `backupCrypto.js`, `atRest.js`, `db-key.js`, `auto-backup.js`, `secure-store.js`, `plain-backups.js`, מסלולי הגיבוי והשחזור ב-`main.js`; הרצת תרחיש תקלה |
| 3. חישובי כסף ודוחות למס | חלקי | `accounting.js`, `pcn874.js`, מספור קבלות בעמותה, סריקה של חישובי נקודה צפה בכל הליבה |

**עוד לא נבדק לעומק** (מומלץ בהמשך): אנדרואיד, שרת הרישוי, סנכרון בין מכשירים, מודול השמאות, מודול האימונים, קובץ מס"ב והמבנה האחיד. כמו כן, בדיקה פנימית אינה מחליפה בודק אבטחה חיצוני — התיק המוכן לו נמצא ב-`docs/SECURITY-AUDIT-BRIEF.md`.

## מה טוב (חוזקות שנמצאו)

- **סיסמאות:** scrypt עם מלח אקראי והשוואה בזמן קבוע; נעילה ל-15 דקות אחרי 5 ניסיונות; מינימום 12 תווים.
- **ניתוק אוטומטי** אחרי 15 דקות בלי פעילות, נבדק בכל פעולה.
- **הרשאות:** כל ערוץ עובר `handle()` → בדיקת כניסה → בדיקת תפקיד → בדיקת רישיון. "צופה" ו"רואה חשבון" לא יכולים לערוך או למחוק. ערוצי המעטפת בודקים שהבקשה הגיעה מהחלון הראשי.
- **הצפנה:** AES-256-GCM עם IV אקראי לכל הצפנה, בדיקת שלמות לפני פענוח, HKDF למפתח נפרד לכל שימוש (מסד, שמאות, אימונים).
- **לא נוצר מפתח חדש מעל נתונים מוצפנים** — אין סכנה לנעילה עצמית.
- **קוד שחזור** עם 2 בתי ביקורת — טעות הקלדה נתפסת.
- **כתיבה בטוחה** (קובץ זמני ואז החלפה) בגיבויים ובמחסן המוצפן.
- **שחזור עם החזרה למצב הקודם** אם משהו נכשל באמצע.
- **כספים באגורות שלמות** בכל הליבה; רשומת יומן לא מאוזנת נדחית (✔ הורץ: חשבונית עם מע"מ שלילי נחסמה).
- **מספור קבלות בעמותה** לא חוזר אחורה גם כששומרים הגדרות (✔ הורץ).
- **CSP מחמיר** בכל המסכים: `script-src 'self'` בלי `unsafe-eval` ובלי סקריפט מוטבע. גם אם טקסט זדוני ייכנס ל-HTML, הדפדפן לא יריץ אותו.

## הממצאים

### ממצא 1 — גבוה — גיבוי שנכשל מדווח "הצליח" ומוחק גיבוי תקין ✔ הורץ

**איפה:** `main.js:438` (`collectBackup`), `modules/econ/core/features.js:148` (`writeEncryptedAutoBackup`). אותו קוד גם ב-`android/web/main-android.js:125`.

**מה קורה:** כשקריאת הנתונים הכספיים נכשלת בזמן הגיבוי (קובץ נעול, תקלת דיסק, מפתח שהשתנה), השגיאה נבלעת לשדה `econError`, והגיבוי ממשיך:

```js
try { out.econ = await econ.getDb().backup(); } catch (e) { out.econError = String(e.message || e); }
```

**תוצאת ההרצה:**
```
status: {"ok":true,"removed":["auto-2026-09-01.ssbk"]}
message: גיבוי אחרון הצליח (2026-10-20 12:00)
new backup econ: null | econError: db-key-mismatch
```

**הנזק:** נוצר גיבוי בלי הכספים, המסך מציג "הצליח", והגיבוי התקין הישן ביותר נמחק. אחרי 14 ימים של תקלה — אין אף גיבוי כספים תקין. גם השחזור האוטומטי של מסד פגום (`DbRecovery.latestAutoBackup`) בוחר את האחרון, הריק, ונכשל. בגיבוי ידני מופיע "הגיבוי נשמר ומוצפן" גם כשהכספים חסרים.

**תיקון:** כשל בקריאת הכספים בגיבוי `all` = כשל של הגיבוי כולו (`reason: 'econ-read-failed'`), בלי כתיבה ובלי מחיקת ישנים. בגיבוי ידני — הודעת שגיאה במקום "נשמר". בדיקת רגרסיה לשני המסלולים.

### ממצא 2 — בינוני — עקיפת רישיון דרך "ייבוא וייצוא נתונים" ומסך הגבייה ✔ הורץ

**איפה:** `shell/licensing/gate.js:47` (`featuresForChannel`), `modules/econ/ipc.js:2414` (`ports:*`), `ipc.js:1173` (`collect:getOverview`).

**מה קורה:** ערוצים שהתחילית שלהם אינה ב-`ECON_SUB_FEATURES` דורשים רק את הרישיון הבסיסי `econ`. אבל:
- `ports:export` / `ports:import` עובדים על המחירון (הנהלת חשבונות), תיקי לקוחות משכנתא ותמיכות עמותה.
- `collect:getOverview` מחזיר את כל דרישות התשלום — חשבוניות, תרומות וגמ"ח.

**תוצאת ההרצה** (רישיון עם `econ` בלבד):
```
acct:getJournal   → התחום הזה אינו כלול ברישיון
npo:getOverview   → התחום הזה אינו כלול ברישיון
ports:export      → ALLOWED
ports:import      → ALLOWED
collect:getOverview → ALLOWED
```

**הנזק:** לקוח שלא שילם על תחום מסוים יכול לייצא ולייבא את הנתונים שלו. אותו סוג בעיה כמו ממצא 6 בסקירה הקודמת (`people:*`), בערוצים שלא נכללו בתיקון. **כרגע אין השפעה — הרישוי כבוי.**

**תיקון:** לכל סוג ב-`dataPorts.KINDS` להצמיד את התחום שלו ולבדוק ב-`ports:*`; לסנן את `collect:getOverview` לפי התחומים הפתוחים (כמו `assertCollectDomain`). להוסיף את שתי התחיליות לבדיקת `licensing-gate`.

### ממצא 3 — בינוני — הגנה חלשה יחסית על גיבוי ידני בסיסמה

**איפה:** `modules/econ/core/backupCrypto.js:5-6`

```js
const MIN_PASSPHRASE = 8;
const SCRYPT = { N: 16384, r: 8, p: 1 };
```

**מה קורה:** ההמלצה של OWASP ל-scrypt היא N=2^17 (131,072) — פי 8 מהערך כאן. יחד עם מינימום של 8 תווים, קובץ גיבוי שאבד (USB) חשוף לניחוש מהיר יותר. בקובץ יש פרטי תורמים, נזקקים ולווים.

**תיקון:** פורמט `v: 2` עם N=2^17, ושמירת הפרמטרים בקובץ — כך שגיבויים ישנים (v1) ממשיכים להיפתח. מינימום 10–12 תווים לגיבוי חדש. (הגיבוי האוטומטי לא מושפע — המפתח שלו אקראי.)

אותו ערך ברירת מחדל משמש גם לסיסמאות המשתמשים (`database.js:812`) — כדאי להעלות גם שם, עם שמירת הפרמטרים ב-hash.

### ממצא 4 — בינוני — שחזור גיבוי ישן מחזיר את מונה החשבוניות והקבלות אחורה

**איפה:** `modules/econ/core/database.js:659` (`restore`) — מחליף את `settings` כולו, כולל `invoiceSeq`, `docSeq` ו-`npo.settings.receiptSeq`.

**מה קורה:** אם משחזרים גיבוי מלפני שבוע, חשבוניות וקבלות שהופקו השבוע נעלמות מהנתונים, והמספרים שלהן יינתנו שוב למסמכים חדשים. מסמך שכבר נמסר ללקוח או דווח לרשות המסים יקבל "כפיל" באותו מספר.

**תיקון:** בשחזור — לשמור לכל מונה את הגדול מבין הערך הנוכחי לערך שבגיבוי, ולהציג בחלון האישור אזהרה כשהגיבוי ישן מהמסמך האחרון שהופק.

### ממצא 6 — נמוך — קובצי ההגדרות נשמרים בלי הגנה מניתוק חשמל

**איפה:** `main.js:354`

```js
function saveJson(f, obj) { try { fs.writeFileSync(f, JSON.stringify(obj)); } catch {} }
```

**מה קורה:** ניתוק חשמל באמצע כתיבה משאיר קובץ שבור, ו-`loadJson` מחזיר `{}`. כך עלולים לאבד את יעד הגיבוי ל-USB (הגיבוי חוזר בשקט לתיקיית המסמכים), את מועד רישום קוד השחזור ואת הגדרות הלוח העברי. גם שגיאת כתיבה נבלעת בלי רישום.

**תיקון:** כתיבה לקובץ זמני והחלפה (כמו בגיבויים), ורישום השגיאה ביומן.
