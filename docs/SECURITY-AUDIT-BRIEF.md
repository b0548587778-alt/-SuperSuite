# תיק לבודק אבטחה חיצוני — SuperSuite

מסמך זה נמסר לבודק אבטחה (Penetration Tester / Code Reviewer) לפני תחילת הבדיקה.
הוא מתאר מה התוכנה שומרת, איך היא מגינה על זה, מה כבר נבדק, ומה ידוע כחסר.
הבדיקה הפנימית האחרונה: [SECURITY-REVIEW-2026-10.md](SECURITY-REVIEW-2026-10.md).

---

## 1. מה המוצר

- תוכנה שולחנית ל-Windows (Electron), **אופליין מלאה**. אין שרת נתונים — כל המידע במחשב של הלקוח.
- גרסת אנדרואיד (APK) מאותו קוד, בלי הצפנה במנוחה (ראו סעיף 6).
- לקוחות: עמותות, גמ"חים, עסקים קטנים, שמאים, מאמני כושר, ובקרוב משרדי נדל"ן ויועצי משכנתאות.
- רכיב רשת יחיד בצד שלנו: **שרת ממסר לרישוי** (`server/license-relay.js`, פריסה ב-`deploy/relay/`). הוא מעביר הודעות חתומות בלבד, ואינו מחזיק נתוני לקוחות. כרגע הרישוי **כבוי בכוונה** (`shell/licensing/root-keys.js` ריק).

## 2. הנכסים — מה שווה לגנוב

| נכס | איפה נשמר | הגנה |
|-----|-----------|------|
| מסד הנתונים הכלכלי (חשבוניות, תורמים, לווים, נזקקים, תיקי משכנתא) | `econ.db` (SQLite) בתיקיית הנתונים | `SSDB1:` + AES-256-GCM על `collections.payload` ו-`audit_events.details`; מפתח = HKDF ממפתח הגיבוי |
| מפתח הגיבוי האוטומטי | `autobackup.key` | DPAPI של Windows; קוד שחזור בן 55 תווים (Base32 של Crockford) |
| נתוני שמאות ואימונים (localStorage) | `secure-shamai.bin`, `secure-trainer.bin` | AES-256-GCM, מפתח לכל מודול (HKDF) |
| תמונות שמאות | IndexedDB של המודול | **לא מוצפן** (ידוע) |
| גיבויים | קבצי `.ssbk` | `SSBK1:` + AES-256-GCM, בסיסמה או במפתח האוטומטי |
| סיסמאות משתמשים | טבלת `auth_users` | scrypt עם salt; נעילה אחרי 5 ניסיונות (`MAX_FAILED_ATTEMPTS`) |
| פרטי חשבון בנק (מס"ב) | בתוך האוסף המוצפן | לא יוצאים לממשק — רק `maskAccount` |
| נזקקים חסויים (חסד) | בתוך האוסף המוצפן | `maskBeneficiary` בצד השרת לכל מי שאין לו `users.manage`, כולל בייצוא |
| קובץ הרישוי | `license-key.bin` | DPAPI + שומר נגד החזרה לאחור (`tests/licensing-tamper.test.js`) |
| יומן תקלות | `crash.log` | כל שורה עוברת `redact` (ת"ז, טלפון, דוא"ל, שם משתמש בנתיב) |

## 3. גבולות האמון — מה מפריד בין מה

1. **מסך ← תהליך ראשי (IPC).** כל מודול הוא `WebContentsView` עם `contextIsolation:true`, `nodeIntegration:false`, `sandbox:true`. כל ערוץ כלכלי עובר ב-`handle()` ב-`modules/econ/ipc.js`: פגישה פעילה ← הרשאת תפקיד (`permissionFor`) ← רישיון (`runGuarded` / `shell/licensing/gate.js`). ערוצים ציבוריים בלבד: `auth:status`, `auth:setup`, `auth:login`, `auth:logout`, `auth:google-login`.
2. **מודול ← מעטפת.** פעולות רגישות (ניווט, גיבוי, שחזור, קוד שחזור) — רק מהמעטפת (`e.sender.id === win.webContents.id`, `shellGuard`). מעבר בין מודולים — `shell/nav-guard.js`.
3. **מודול ← מודול.** ערוצי המחסן המוצפן בודקים `fromModuleView`: שמאות לא קוראת נתוני אימונים ולהפך.
4. **קובץ ← תוכנה.** פרוטוקול `app://` מגיש רק מ-`modules/<mod>/`, עם חסימת path traversal אחרי `path.normalize`.
5. **רשת ← תוכנה.** CSP מחמיר בכל חלון (`script-src 'self'`, בלי `unsafe-eval`). `tests/no-network.test.js` סורק את כל הקבצים הארוזים. קישורים נפתחים בדפדפן המערכת.
6. **קוד הפצה.** `devTools:false`, יציאה על פרמטר דיבוג, `electronFuses` (בלי `runAsNode`, בלי `NODE_OPTIONS`, בדיקת שלמות `app.asar`), כיווץ קוד ב-CI.
7. **כניסה עם Google (אופציונלית).** דפדפן המערכת + 127.0.0.1, PKCE ו-state, אימות מלא של `id_token`. לא נשמר אסימון — רק `sub`.
8. **שרת הממסר.** הודעות חתומות (Ed25519) וסודיות קדימה; ראו `tests/licensing-relay-hardening.test.js` ו-`tests/relay-security-review.test.js`.

## 4. מה מבקשים מהבודק לנסות

**עדיפות גבוהה:**
- מתוך מסך של מודול (למשל ארגז הכלים, שאינו דורש כניסה) — להפעיל ערוץ כלכלי, לגבות, לשחזר, או לקרוא נתוני מודול אחר.
- לעקוף את מסך הכניסה, את הנעילה אחרי ניסיונות כושלים, או את חלוקת התפקידים (משתמש "צופה" / "רואה חשבון" שמבצע כתיבה או מחיקה).
- לקרוא את מסד הנתונים, את המחסנים או את הגיבויים מחוץ לתוכנה (משתמש אחר באותו מחשב, דיסק שהוצא, קובץ גיבוי שנשלח בדוא"ל).
- להזריק סקריפט דרך נתונים (שם תורם, תיאור חשבונית, קובץ CSV מיובא, vCard, קובץ טבלת שכר, לוגו) ולראות אם הוא רץ במסך או במסמך להדפסה/PDF.
- לטעון קובץ גיבוי זדוני או פגום בשחזור (נתוני אימונים, גיבוי ישן לא מוצפן).
- path traversal בפרוטוקול `app://` ובשמות קבצים שהמעטפת שולחת.
- לעקוף את הרישוי (כשיופעל): החזרת שעון, מחיקת קובץ הרישוי, העתקה בין מחשבים, זיוף תשובת שרת.

**עדיפות בינונית:**
- להריץ את ההפצה עם פרמטרים של Node / Chromium, לשנות את `app.asar`, ולבדוק שהיא מסרבת לעלות.
- לבדוק שאין מידע רגיש ביומן התקלות ובדוח התקלה.
- שרת הממסר: הצפה, הודעות חוזרות (replay), גישה לתיבה של לקוח אחר.
- אנדרואיד: מה נחשף ב-`adb backup` ובאחסון האפליקציה.

## 6. חסרים ידועים — לא לדווח כממצא חדש, כן להעריך חומרה

1. **אנדרואיד — הנתונים לא מוצפנים במנוחה** (אין שם DPAPI ואין `dbOptions`).
2. **תמונות השמאות (IndexedDB) — לא מוצפנות.**
3. **הרישוי כבוי** עד תחילת המכירה (ממצא #3 בבדיקה הפנימית — החלטה מכוונת).
4. **מחשב בלי DPAPI** — המסד נשמר גלוי עם אזהרה במסך הבית.
5. **אין חתימת קוד** ל-EXE עדיין (ממתין לתעודה, ראו `docs/CODE-SIGNING.md`).
6. מי שיש לו גישה לחשבון Windows של המשתמש (כשהוא מחובר) יכול לפתוח את DPAPI — זה גבול האמון שבחרנו.

## 7. איך להריץ

- **התקנה:** קובץ ההתקנה מ-GitHub Actions (`Build Windows installer`) — לקבל מהבעלים.
- **מקוד:** `npm ci` ואז `npm start` (Node 22 ומעלה).
- **בדיקת עלייה בלי ממשק:** `node_modules/electron/dist/electron.exe . --smoke --user-data-dir=<תיקייה זמנית>`.
- **נתונים לבדיקה:** במסך הבית ← "נתוני דוגמה". אין להשתמש בנתוני לקוח אמיתיים.
- **פרופיל נפרד:** תמיד `--user-data-dir=<תיקייה>`, וכתבו בה `backup-settings.json` עם `targetDir` בתוך התיקייה — אחרת הגיבוי האוטומטי נכתב לתיקיית הגיבוי האמיתית.

## 8. כללי עבודה

- הבדיקה רק על עותק בדיקה ובמחשב של הבודק. **לא** על מחשב של לקוח ו**לא** על שרת הממסר בהפצה בלי תיאום מראש בכתב.
- הסכם סודיות (NDA) לפני קבלת הקוד.
- לא להעלות את הקוד או הממצאים לשירות חיצוני (כולל כלי AI ציבוריים) בלי אישור.
- ממצא חמור — לדווח מיד, לא בסוף.
- **פורמט הדוח:** לכל ממצא — כותרת, חומרה (CVSS או קריטי/גבוה/בינוני/נמוך), שלבי שחזור, השפעה, והמלצה. הדוח בעברית או באנגלית.
- בסיום — בדיקה חוזרת של התיקונים (re-test) כלולה בהצעת המחיר.
